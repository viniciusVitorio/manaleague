# Arquitetura

## Componentes

| Componente | Responsabilidade |
|---|---|
| Browser | interface e envio de formularios com CSRF |
| Cloudflare (Free) | DNS, proxy reverso na borda, protecao DDoS, Free Managed Ruleset e rate limit das rotas de autenticacao |
| Caddy | porta publica (80/443), TLS automatico (Let's Encrypt), IP real via `CF-Connecting-IP`, compressao, headers e proxy reverso para o WAF |
| WAF: Nginx + ModSecurity v3 + OWASP CRS v4 | imagem oficial `owasp/modsecurity-crs` (tag LTS fixa, sem porta publicada): inspeciona toda requisicao com o **OWASP Core Rule Set**, serve o `public/` e passa so o `index.php` para o PHP-FPM |
| Laravel/PHP-FPM | autenticacao, autorizacao, round-robin, ranking, finais e headers de seguranca (`SecurityHeaders`) |
| Laravel Reverb | tempo real (WebSocket, protocolo do Pusher): servico `reverb` do Compose, mesma imagem do app, sem porta publicada; o Caddy encaminha so `/app/*` |
| PostgreSQL 17 | usuarios, torneios, jogadores, partidas, sessoes, cache e fila (servico `db` do Compose, volume `pg_data`, sem porta publicada) |
| Amazon S3 (privado) | fotos de perfil (`avatars/<uuid>.webp`), lidas pelo navegador via URL assinada |
| GitHub Actions | CI, scanners, quality gate e CD |
| SonarQube Cloud | analise estatica e Quality Gate |
| Terraform | EC2, chave e firewall reproduziveis |

## Fluxo de requisicao

```text
Internet → Cloudflare (DDoS, Free Managed Ruleset, rate limit) → Security Group :80/:443 (so faixas da Cloudflare)
         → Caddy (TLS, IP real) → Nginx + ModSecurity/OWASP CRS (WAF) → PHP-FPM/Laravel → PostgreSQL
                ↘ headers                  ↘ 403 "Requisicao bloqueada"      ↘ CSP/HSTS/XFO (middleware)
```

## Fluxo de entrega

```text
Commit → PHPUnit → Composer Audit/Trivy → Sonar → Quality Gate
                                                       │
                                               aprovado │
                                                       ▼
                                    WAF: build unico + smoke tests
                                                       │
                                      artifact da imagem + SHA256
                                                       │
                                    SSH → EC2: verifica/importa → Compose --no-build
```

## Confirmacao de e-mail (ML-102)

Novos cadastros criam conta/perfil e enviam um link temporario assinado pelo transporte de e-mail existente. Recursos autenticados, inclusive canais privados, exigem confirmacao; tela de espera, reenvio e logout continuam acessiveis. A migration preserva o acesso das contas anteriores por uma flag controlada pelo servidor, sem inventar uma data de confirmacao. Falha no envio mantem a conta pendente com erro recuperavel. Fluxo, compatibilidade e requisitos do provedor em [email-verification.md](email-verification.md).

## Decisoes

- **PostgreSQL no Compose:** substituiu o SQLite (escrita concorrente, tipos rigidos e backup com `pg_dump`) sem custo extra de RDS: roda na propria EC2, ajustado para a t3.micro (`shared_buffers=64MB`, `max_connections=40`, `mem_limit` 256 MB), so na rede interna do Docker e com senha SCRAM vinda do secret `DB_PASSWORD`. A CI roda a suite inteira no PostgreSQL; localmente o `phpunit.xml` continua em SQLite em memoria (rapido), e `DB_CONNECTION=pgsql` no ambiente troca o banco dos testes.
- **Migracao SQLite → PostgreSQL:** `php artisan db:import-sqlite <arquivo> [--if-empty] [--force]` cria o esquema pelas migrations e copia os dados tabela a tabela, em ordem de chave estrangeira e numa unica transacao (falhou = nada gravado); converte 0/1 em booleano, ignora colunas/tabelas que nao existem mais no codigo, ajusta as sequencias dos ids e confere as contagens. No 1o boot do container com Postgres o `entrypoint` roda a importacao do banco antigo do volume (`storage/app/database.sqlite`, so se o Postgres ainda nao tiver usuarios) e renomeia o arquivo para `database.sqlite.migrado-<data>`; o deploy guarda antes uma copia em `/opt/manaleague/database-pre-postgres.sqlite`.
- **Docker Compose:** reproduz o mesmo runtime local e na EC2.
- **Imagem pre-construida na CI:** o job WAF executa `docker compose build app` uma unica vez com `APP_IMAGE=manaleague-app:<commit SHA>`, inicia app/Reverb com `--no-build` e preserva todos os testes WAF, IP forjado e WebSocket. So depois dos smoke tests exporta a mesma imagem com `docker save | gzip -1` e SHA256 em `RUNNER_TEMP/app-image` (fora do checkout/pacote fonte). O artifact `app-image-<commit SHA>` e publicado tambem em PR, retido por um dia e sem recompressao pelo upload. No push da main, o deploy baixa o artifact desta mesma execucao (nunca de outra run ou de evento release), envia por SCP e grava a tag em `deploy.env`. A EC2 verifica o checksum antes de `docker load` e confere a tag com `docker image inspect`, antes de trocar `current`; app/Reverb sobem com `--no-build`. Imagens oficiais de Caddy/WAF/Postgres continuam baixadas por tag fixa. Nao requer registry, secret novo, aumento da instancia nem compilacao na EC2. A mudanca remove o build remoto que foi encerrado com `signal: killed`; sem logs do kernel, nao se afirma OOM como causa comprovada.
- **Caddy na borda:** emite e renova o certificado TLS sozinho (Full strict na Cloudflare) e resolve o IP real; o WAF fica atras dele, numa rede interna do Docker.
- **WAF em duas camadas:** a Cloudflare Free segura volume (DDoS, rate limit, regras gerenciadas basicas); o OWASP CRS completo roda na origem com a **ModSecurity v3** (servico `waf` do `docker-compose.yml`, imagem oficial `owasp/modsecurity-crs`), porque o CRS da Cloudflare so existe no plano Pro. Configuracao do CRS por variavel de ambiente da imagem: paranoia 1, limiar de anomalia 5, metodos `PUT/PATCH/DELETE` liberados, limites de corpo (8 MB com arquivo, 256 KB sem) e respostas fora da inspecao. Excecoes do projeto em `deploy/modsecurity/RESPONSE-999-EXCLUSION-RULES-AFTER-CRS.conf` (senhas, token CSRF e cookies do Laravel fora da inspecao; nunca uma regra inteira desligada). Nginx do WAF em `deploy/modsecurity/nginx/` e pagina de bloqueio em `deploy/modsecurity/blocked.html` (resposta 403 com `X-WAF-Block`). `WAF_MODE=DetectionOnly` (variavel do GitHub) vira `MODSEC_RULE_ENGINE` e so registra, para investigar falso positivo sem deploy de codigo. Regras disparadas aparecem em `docker compose logs waf` (error log com id/mensagem e audit log JSON com partes `AHZ`, sem corpo nem cookies). A CI (job `WAF`) sobe a stack inteira e roda `docker/waf/waf-smoke.sh`: trafego legitimo do app nao pode ser bloqueado e ataques classicos (SQLi, XSS, LFI, RCE, PHP injection, scanner, Log4Shell, TRACE) precisam ser.
- **IP real atras do proxy:** o Caddy so aceita `CF-Connecting-IP` vindo das faixas da Cloudflare (`deploy/caddy/cloudflare-trusted-proxies.caddy`, conferido pela CI) e repassa em `X-Real-IP`; o Nginx do WAF so confia nesse cabecalho vindo da rede interna e entrega o IP como `REMOTE_ADDR` ao PHP. A ModSecurity registra e o throttle do Laravel conta por visitante (a CI confere que `CF-Connecting-IP`/`X-Real-IP` forjados sao ignorados).
- **Formularios sem recarregar a pagina:** `public/js/async-forms.js` (no layout principal) envia todo `<form method="POST">` com `fetch()` e o cabecalho `X-ManaLeague-Async: 1`. Os controllers nao mudam: o middleware `AsyncFormRedirects` (primeiro do grupo `web`) troca o redirect por `200 {"redirect": url}`, entao a mensagem flash e os erros de validacao continuam na sessao. Se a URL final e a mesma pagina, o script busca a pagina e atualiza o `<body>` no lugar com Idiomorph (`public/js/vendor/idiomorph.min.js`, 0BSD): rolagem, foco, `<details>` abertos e ouvintes ficam. Outra URL (criar torneio, login, excluir) navega normalmente. Mensagens fora da tela viram aviso no canto; 419/403/429/erro de rede tambem. Fica de fora: GET, `target="_blank"` e `data-async="off"`; `data-async-keep` protege um elemento da atualizacao (ex.: resultados da busca de cartas). Scripts de tela usam eventos delegados ou o evento `manaleague:updated`, e `window.ManaLeague.refresh()` atualiza a tela depois de um `fetch` proprio.
- **Headers na aplicacao e no proxy:** defesa em profundidade; trocar o proxy nao remove as protecoes.
- **Tempo real (Laravel Reverb):** o Reverb so **avisa** "esta tela mudou"; o dado continua vindo dos endpoints HTTP de sempre (com policy, allowlist e ETag). Um observer (`LiveChangeObserver`) nos models que as telas ao vivo mostram (torneio, inscricao, partida, envio de placar, desafio, partida casual, Ranked e envios, notificacao) junta os canais afetados (`LiveChannels`) e o `RealtimeService` publica uma vez so, depois da resposta (`terminating`), com `ShouldBroadcastNow` (sem fila nem worker). Canais: `private-user.{id}` (tudo da pessoa, escopo `me`), `private-tournament.{id}`, `private-challenge.{id}`, `private-ranked.{id}`, `private-life.{mesa}` e o publico `arena.{slug}` (Modo TV/pagina publica). O `live-refresh.js` (escopos de `@section('live-scope')`) e o `live.js` (arena) assinam os canais da tela e perguntam a versao na hora; com o canal assinado o polling vira garantia (30s/60s), sem socket volta a 5s/10s. Notificacao nova vira aviso clicavel e +1 no sino em qualquer pagina (`live-notify.js`). Cliente proprio do protocolo do Pusher (`public/js/realtime.js`, sem biblioteca externa) na mesma origem; a CSP libera `wss://` do proprio host. Chave e segredo do Reverb saem do `APP_KEY` por HMAC (sem secret novo no deploy); `REVERB_APP_KEY`/`REVERB_APP_SECRET` sobrescrevem. Reverb fora do ar nunca derruba uma pagina (`report()` e segue). `BROADCAST_CONNECTION=null` desliga tudo (padrao nos testes e fora do Docker). Update em massa (query builder) nao dispara observer: essas telas se atualizam pelo polling.
- **Contador de vida compartilhado:** cada partida (torneio, Ranked, desafio) tem uma mesa (`life_tables`, criada ao abrir o contador) com a lista de jogadas em ordem (`life_ops`). O servidor nao calcula vida: valida o formato da jogada, da a ordem (`seq`, com lock) e repassa pelo canal `private-life.{mesa}`; cada celular aplica as mesmas jogadas na mesma ordem (`public/js/life-core.js`, testado em node) e chega ao mesmo placar. Jogadas sao variacoes (toques simultaneos somam); fim de game, reiniciar e encerrar levam o game, e desfazer leva o tamanho da pilha, entao jogada atrasada vira nada. O celular mostra o toque na hora (pendente), envia em lote e, sem internet, guarda no `localStorage` e reenvia sem duplicar (`client_id` unico por mesa); sem socket, pergunta a cada 3s. O resultado final continua indo pelo endpoint canonico de cada partida; quando um celular envia, o outro mostra "Fulano enviou o resultado" com o link para confirmar. O contador so existe vinculado a uma partida: nao ha mesa avulsa, menu proprio nem entrada por codigo/QR.
- **Volumes nomeados:** preservam banco e dados entre releases.
- **Releases imutaveis:** cada commit e extraido em uma pasta e um symlink `current` e trocado.
- **SSH efemero no CI:** o IP `/32` do runner e autorizado somente durante o deploy e revogado no final.
- **Servicos de dominio:** `PairingService` gera confrontos e `StandingsService` calcula a tabela sem misturar regra de negocio com HTML.
- **Maquina de estados do torneio:** `setup → league → finals → finished`; cada transicao valida o estado atual com lock, e placares so podem ser editados na fase da partida.
- **Pagina publica tokenizada:** amigos acompanham o placar sem conta, mas nao recebem endpoint de escrita. Ela traz meta tags Open Graph (formato, data, jogadores e lider/campeao) para a previa do link no WhatsApp.
- **Nome de usuario (endereco do perfil):** o `handle` e separado do nome de exibicao (`nickname`) e vira o link `/p/{handle}`; e gerado do nome no cadastro e depois escolhido pelo jogador (3-30 caracteres `a-z0-9-`, lista de reservados, uma troca a cada 30 dias, `throttle:10,1`). Trocar o nome de exibicao nao muda o usuario. O endereco anterior fica reservado por 90 dias em `profile_handle_holds` e redireciona (302) pelo `missing()` da rota; quem nao pode ver o perfil recebe 404. O endereco antigo `/players/{id}` tambem redireciona com 302 (o destino pode mudar), so para quem pode ver o perfil, com `throttle:30,1` contra varredura.
- **Data da lista do deck:** `decks.cards_updated_at` muda nos eventos `created/updated/deleted` de `DeckCard` (e na importacao com "substituir", que apaga em massa). Nome, capa e deck principal nao contam.
- **Exportar deck:** "Copiar lista" usa `DeckBuilderService::exportText`, no formato do Arena (`Commander` / `Deck` / `Sideboard`), aceito pela LigaMagic, pelo Moxfield e pelo importador do proprio ManaLeague. "Baixar .csv" (`/decks/{deck}/export`, com a `DeckPolicy`) usa `exportCsv`: as colunas do CSV do ManaBox, na mesma ordem, mais `Board` no fim. Nome da colecao, numero de colecionador e idioma vem do Scryfall pela edicao salva (`byIds`, lotes de 75); se o Scryfall falhar, essas colunas saem vazias. A coluna `Foil` sai do acabamento da carta no deck; sem preco de compra ou condicao no deck, saem vazio e `near_mint`.
- **Foil no deck:** `deck_cards.foil` guarda o acabamento (normal ou foil, como a colecao); a mesma edicao pode estar nas duas versoes (`unique(deck_id, scryfall_id, board, foil)`). Mover entre deck e sideboard leva o acabamento junto. Na importacao de lista, `*F*`/`*E*` do Moxfield viram foil. A condicao fica so na colecao (e da carta fisica, nao do deck). "O que falta" no modo exato compara edicao e acabamento; pelo nome, nao.
- **Adicionar cartas da colecao:** quem tem colecao escolhe, no deck, buscar no Scryfall ou em "Minha colecao" (`/me/collection/search`, so as cartas da propria pessoa, mesmo JSON da busca do Scryfall mais `owned` e `foil`; foil e normal separados, condicoes somadas). Adicionar usa o mesmo formulario: o servidor busca a carta no Scryfall pelo ID e grava o acabamento do resultado. Na busca do Scryfall, a caixa "Adicionar como foil" define o acabamento.
- **Importar CSV do ManaBox na colecao:** `CollectionService::importCsv` le pelas colunas do cabecalho (ordem livre, extras ignoradas, virgula ou ponto e virgula, UTF-8 ou Windows-1252), ate 2.000 linhas de ate 2 MB. A carta vem do Scryfall pelo `Scryfall ID` (`byIds`); sem ID, pelo nome e edicao. `Foil` = foil/etched; condicoes do ManaBox viram as da colecao (mint/near_mint NM, excellent LP, good/light_played MP, played HP, poor DMG). Aceita tambem o .csv de deck baixado no ManaLeague.
- **Sem estatisticas de decks no torneio:** fica de fora por escolha (porcentagem de decks, cores e custos dos participantes). Seria redundante com os decks individuais e poderia expor o que os jogadores nao querem mostrar.
- **Cartas banidas:** `card_bans` guarda a lista de banidas por formato (Pauper, Commander, Standard, Modern, Pioneer, Legacy), copiada do Scryfall por `cards:sync-bans` (no deploy e todo dia pelo workflow `daily-tasks.yml`; se o Scryfall falhar, a lista anterior fica e o comando sai com erro). A comparacao e pelo nome da carta. Draft e Outro nao tem lista. O deck mostra a tag "Banido" nas cartas banidas no formato dele.
- **Cartas invalidas no Pauper:** `deck_cards.pauper_legality` guarda o `legalities.pauper` do Scryfall (`legal`, `not_legal`, `banned`), gravado quando a carta entra no deck. Vale para a carta inteira (todas as impressoes), entao a raridade da edicao salva nunca decide. Em deck de Pauper, `not_legal` vira a tag "Invalida" e barra o deck em torneio com as regras do formato, como a banida (`BanListService::blockedByDeck`). Cartas antigas ficam sem marca ate `cards:sync-legality` preencher (no deploy e todo dia pelo `daily-tasks.yml`); o comando sai com erro se o Scryfall nao responder.
- **Tarefas diarias:** `.github/workflows/daily-tasks.yml` roda `cards:sync-bans`, `cards:sync-legality` e `challenges:auto-confirm` na producao as 06:00 de Brasilia, e pelo botao "Run workflow" (Actions > Daily tasks, escolhendo todas ou uma so). Abre o SSH so para o IP do runner, como o deploy, e divide a fila `manaleague-production` com ele. O Docker de producao nao tem agendador do Laravel, por isso o agendamento fica no GitHub.
- **Regras do torneio:** `rules` = `standard` (padrao do formato: banidas nao entram) ou `custom` (o organizador escolhe `allow_banned` e pode escrever `house_rules`). Torneio ranqueado nao aceita banidas. Quando o torneio barra banidas (`Tournament::blocksBannedCards`), o deck vinculado e conferido na inscricao pelo convite, na troca de deck, no amigo adicionado pelo organizador (deck principal), no check-in (jogador e organizador) e ao iniciar. O organizador ve so a marca "Deck invalido", sem a lista de cartas.
- **Deck da inscricao:** so vale deck salvo na conta do jogador, do formato do torneio ou sem formato definido (`Tournament::acceptsDeck`; "Outro" aceita qualquer formato). Nao existe deck digitado: `deck_name`/`deck_colors` sao copia do deck para o historico, e as telas mostram o nome atual do deck (`Player::deckLabel`); sem deck vinculado, quem tem conta aparece como "Deck nao informado" (o nome digitado nao vale como deck). Convite e troca exigem um deck (`TournamentEntryController::validatedDeck`); o amigo adicionado pelo organizador precisa de um deck principal do formato. No Draft o deck e opcional (montado na mesa). Inscrito com conta e sem deck (inscricoes antigas, deck apagado, torneio repetido) recebe a marca "Sem deck", nao faz check-in e impede o inicio (`Tournament::playersWithoutDeck`). So o proprio jogador ve o aviso "Cadastre seu deck para este torneio" na inscricao e a pendencia no painel. Jogador sem conta nao tem decks e fica de fora dessa regra.
- **Repetir torneio:** copia formato, sistema, regras (incluindo as personalizadas), cronometro e, opcionalmente, os jogadores (sem check-in e sem resultados); links novos; o clube so continua se quem repete ainda organiza o clube.
- **Foto de perfil no S3 privado:** o upload passa pelo Laravel (`AvatarService`), que valida, reencoda em WebP 256x256 (descarta EXIF e payloads) e grava com nome UUID. As views usam o componente `<x-avatar>` (foto ou emoji/inicial). Com `AVATAR_DISK=s3` o navegador recebe *presigned GET* com inicio arredondado a janelas de 30 min (mesma URL = cache do navegador) e validade de janela + 90 min; a CSP libera so a origem do bucket. Com `AVATAR_DISK=local` (padrao em dev e no deploy ate o bucket existir) a rota `/avatars/{uuid}.webp` serve o arquivo do volume.

### Integracao entre modulos

- `Community\CommunityEvents` e o unico ponto que transforma eventos de dominio em notificacoes e atividades do feed. E chamado depois do commit por `TournamentFlowController` (inicio, avanco, finais), `MatchController`, `MatchResultSubmissionService` (envio, contestacao, confirmacao/resolucao) e `ChallengeService` (convite, aceite/recusa/cancelamento, placar, confirmacao).
- Toda chave de evento e estavel (`tournament:{id}:round:{n}:...`, `submission:{id}:...`, `challenge:{id}:...`): repetir a chamada nunca duplica notificacao ou atividade.
- A visibilidade e recalculada a cada leitura (`CommunityAccess`): organizador e membros do clube veem o torneio; jogadores inscritos com conta veem eventos do proprio torneio (somente leitura, link para a arena publica). Quem nao participa nao ve nada.
- Silenciar uma categoria nas preferencias (`match`, `tournament`, `challenge`, `club`, `achievement`) silencia todos os tipos dela (`match.submitted`, `match.disputed`...).
- Resolucao de contestacao usa a policy de torneio: dono ou organizador de clube resolvem; membro comum nao.
- Placar enviado pelo celular segue as mesmas regras do placar do organizador (fase editavel, sem empate em eliminacao/finais); mesas Commander sao lancadas pelo organizador.
- Os decks sao congelados (`DeckVersionService::snapshotForTournament`) dentro da transacao de inicio do torneio.

### Deploy

- As migrations `2026_10_20_*` rodam sozinhas no `docker/entrypoint.sh` (`php artisan migrate --force`). Todas foram testadas em banco limpo, com rollback e reaplicacao.
- Nova dependencia: `bacon/bacon-qr-code` (PNG gerado localmente, sem GD/Imagick e sem servico externo; o token do convite nunca sai do servidor).
- Nao ha fila nem cron novos: notificacoes sao gravadas na hora (somente no app, sem e-mail) e desafios expiram de forma preguicosa ao abrir as paginas.
- **Confirmacao automatica de desafio:** placar de desafio (casual ou ranqueado) sem resposta do adversario por `Challenge::CONFIRM_DAYS` (7) dias e confirmado sozinho por `ChallengeService::autoConfirmOverdue`, ao abrir Desafios, um desafio, Minhas partidas ou a partida ranqueada, e todo dia pelo `daily-tasks.yml` (`challenges:auto-confirm`). O prazo conta do envio do placar (`casual_matches.reported_at`; no Ranked, o envio pendente) e recomeca a cada novo envio. Placar contestado nao entra. Os dois recebem aviso e a partida fica marcada (`auto_confirmed`).
- Todos os CSS/JS usam `VersionedAsset::url`, entao cada deploy invalida o cache do navegador automaticamente.
- Fotos de perfil: a imagem Docker passa a ter `gd` (JPEG/PNG/WebP) e `exif`; a migration `2026_10_26_*` cria `player_profiles.avatar_path`. Ativar o S3 em producao:
  1. `terraform apply` (cria o bucket privado e a policy `s3-profile-photos` na role da EC2; revise o plano: nao pode haver `-/+` na instancia);
  2. no GitHub (Settings > Secrets and variables > Actions > Variables): `AVATAR_DISK=s3` e `AVATAR_BUCKET=<output avatar_bucket>`;
  3. novo deploy. Sem essas variaveis as fotos ficam no volume local (`storage/app/private/avatars`); fotos enviadas antes da troca nao sao copiadas sozinhas (`aws s3 sync` do volume para o bucket, se houver).
